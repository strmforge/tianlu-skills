# Agent Platform Lifecycle Review

Status: incubating

Scope: runtime-neutral review method

## Signal

Controller-audited public repositories increasingly present agent platforms as complete lifecycle systems rather than single skills or prompt files. The recurring shape combines prompt development, debugging, evaluation, observability, memory, self-evolution, skills, plugins, workflows, visual builders, and ingestion tools.

This candidate keeps that shape in incubation. It does not endorse any platform, crawler, curriculum, marketplace, installer, hosted service, or local runtime.

## Source Evidence

Controller-audited local QClaw short-worker receipts from 2026-06-25 include source-review evidence for:

- skill collection and legal rule hierarchy packages with validation or priority claims;
- durable workflow engines and context-engineering runtimes;
- official curriculum-style course packs;
- agent-harness packages that advertise planning, memory, knowledge, skills, and self-evolution;
- lifecycle platforms that separate prompt development, evaluation, and observability;
- visual agent builders that combine prompt, RAG, plugin, workflow, API, and deployment surfaces;
- web-to-LLM Markdown crawlers with filtering, caching, API, progressive crawl, security, and prompt-template surfaces.

The receipts are evidence packets, not neutral law. A worker summary is accepted only after controller path verification, source spot-check, and conflict correction. For example, one self-evolution package had README support for a three-tier memory story, while a controller spot-check of its config surface only found flat self-evolution toggles and agent workspace/context settings, not proof of an explicit three-tier config schema.

## Proposed Trigger

Use this candidate when a repository, product, or internal proposal claims to provide an all-in-one or lifecycle agent platform with several of these surfaces:

- prompt development, prompt debugging, or prompt versioning;
- eval sets, evaluators, experiment management, or multi-dimensional evaluation;
- trace capture, observability, monitoring, dashboards, logs, or session viewers;
- long-term memory, knowledge bases, self-evolution, reflection, distillation, or automatic skill improvement;
- skills, plugins, workflows, RAG, databases, or resource catalogs;
- low-code or no-code builders, API/SDK integration, deployment, or hosted runtime claims;
- web crawling, web-to-Markdown extraction, content filtering, progressive crawl state, or LLM-ready data pipelines;
- curriculum, course, or index material presented as a practical agent-development method.

## Proposed Mechanism

Review the platform as separate lifecycle planes before any adoption:

1. Separate curriculum from runtime.
   - A course, index, or tutorial sequence may be useful absorb-layer material, but it is not an executable method or local activation proof.
2. Separate prompt development from evaluation.
   - Playground comparisons, prompt versioning, evaluator management, and experiment summaries are distinct evidence surfaces.
3. Separate observability from authority.
   - Trace capture, dashboards, intermediate results, and exception logs can reduce uncertainty, but do not authorize unattended loops, deployment, account access, or system writes.
4. Treat memory and self-evolution as persistent behavior.
   - Memory tiers, nightly distillation, automatic skill improvement, and unfinished-task follow-up require source, retention, rollback, owner-review, and activation boundaries.
5. Treat visual builders as multi-surface products.
   - Prompt, RAG, plugin, workflow, database, API, SDK, model, deployment, and low-code surfaces each need their own authority and rollback review.
6. Treat crawlers and web-to-LLM pipelines as ingestion systems.
   - Source status, egress, robots or terms constraints, authentication, CAPTCHA/proxy handling, data retention, security hardening, and prompt-template use are separate review surfaces.
7. Do not let popularity or commercial origin validate behavior.
   - Stars, enterprise counts, hosted versions, open-source editions, and commercial provenance are context, not validation.
8. Keep executable and external surfaces inactive.
   - Installs, package runs, browser automation, crawlers, hosted services, provider calls, API keys, web consoles, plugins, skill hubs, model configuration, deployments, commits, pushes, and external services need scoped activation review.
9. Add eval before promotion.
   - Compare lifecycle-platform review against a smaller role-package review and a single-tool intake baseline on routing precision, evidence separation, activation boundary handling, and false completion.

## Initial Scope

- Agent platform, lifecycle platform, visual builder, self-evolution, and ingestion-pipeline claims.
- Source-review synthesis only.
- Not a runtime adapter.
- Not an install guide.
- Not a claim that a platform is safe, current, compliant, or production-ready.

## Known Failure Modes

- Platform completeness theater: a platform lists all lifecycle stages but only implements a shallow demo.
- Self-evolution laundering: memory or reflection language is treated as permission to write durable state or change future behavior.
- Observability laundering: traces and dashboards are treated as proof of correctness or loop authority.
- Builder authority creep: a no-code workflow canvas is treated as permission to create, deploy, publish, or mutate systems.
- Crawler compliance overreach: web-to-Markdown usefulness is treated as permission to crawl accounts, bypass access controls, use CAPTCHA or proxy services, retain data, or publish extracted content.
- Curriculum-runtime confusion: educational course order is treated as a validated runtime workflow.
- Proof by popularity: stars, user counts, commercial origin, or hosted availability are treated as independent validation.
- Schema theater: named memory tiers, eval dimensions, or workflow modules are repeated without checking where they exist in code, config, docs, or runtime behavior.
- Source-to-law jump: one strong platform becomes neutral Tianlu law without replay, negative cases, or adapter review.

## Verification Needed

- Replay on several lifecycle platforms and compare against role-package and tool-intake baselines.
- Sample whether advertised memory, evaluation, observability, and workflow planes have distinct source artifacts.
- Check whether self-evolution claims have real state, retention, rollback, and review controls.
- Check whether crawler or ingestion claims preserve source role, egress, security, and compliance boundaries.
- Add negative eval cases for platform-completeness claims, self-evolution as durable-memory authority, observability as validation, and crawler usefulness as web-action authority.
- Decide whether this remains a supporting incubator note or becomes a productive platform-review playbook.
